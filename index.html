Post-mortem: error en un formulario de contacto

Análisis constructivo de un incidente y sus aprendizajes

Resumen ejecutivo

Un formulario de contacto mostraba el mensaje “Enviado correctamente”, pero las consultas no se registraban. El problema fue detectado, investigado y corregido. A partir del análisis post-mortem también se incorporaron controles para prevenir incidentes similares.

1. Contexto

El incidente ocurrió en el sitio web de un pequeño emprendimiento que utilizaba un formulario para recibir consultas de potenciales clientes. Este canal permitía solicitar información sobre productos, precios y disponibilidad.

El objetivo era ofrecer una forma rápida y sencilla de comunicación. Sin embargo, durante una revisión se descubrió que el formulario confirmaba el envío sin comprobar si la información había sido registrada correctamente.

2. Problema e impacto

Las personas completaban el formulario y veían el mensaje “Enviado correctamente”, pero la consulta no llegaba al sistema.

Impacto

  • Se perdieron posibles consultas de clientes.
  • Los usuarios recibieron una confirmación incorrecta.
  • El equipo no pudo responder los mensajes.
  • Se afectó la confianza en el canal de contacto.

3. Investigación y causa

Para investigar el incidente se reprodujo el recorrido completo: completar el formulario, enviarlo y verificar si la información se almacenaba correctamente.

Se identificó que el mensaje de confirmación aparecía automáticamente después de presionar el botón, sin validar el resultado real del envío.

La causa estuvo relacionada con la falta de una validación técnica y de una prueba completa del recorrido del usuario antes de publicar el formulario.

El análisis se realizó de manera constructiva y sin buscar responsables individuales. El objetivo fue comprender qué parte del proceso había permitido que el error llegara a producción y cómo mejorarla.

4. Cronología del incidente

  • Detección: se identificó que las consultas enviadas desde el formulario no se estaban registrando.
  • Reproducción: se realizó una prueba completa para confirmar el problema.
  • Investigación: se detectó que el mensaje de éxito aparecía sin comprobar el resultado real del envío.
  • Corrección: se modificó la validación para mostrar la confirmación solamente cuando el envío finalizara correctamente.
  • Verificación: se realizaron pruebas con datos válidos, inválidos y campos vacíos.
  • Prevención: se definieron nuevos controles y pruebas previas para futuros cambios.

5. Acciones correctivas y preventivas

Acciones correctivas

  • Se corrigió la validación del envío.
  • El mensaje de éxito aparece únicamente cuando la operación finaliza correctamente.
  • Se agregó un mensaje claro para los casos de error.
  • Se realizaron pruebas con diferentes tipos de datos.

Acciones preventivas

  • Crear una lista de verificación antes de publicar formularios.
  • Probar todo el recorrido desde la perspectiva del usuario.
  • Registrar errores para facilitar futuras investigaciones.
  • Revisar cambios mediante commits y Pull Requests.
  • Documentar los incidentes y las soluciones aplicadas.

6. Resultado

Después de implementar la corrección, el formulario fue probado nuevamente. Las consultas comenzaron a registrarse correctamente y el mensaje de confirmación quedó asociado al resultado real del envío.

La solución permitió recuperar la confiabilidad del canal y establecer un proceso de control más claro para futuras publicaciones.

7. Aprendizajes

  • Una confirmación visual no garantiza que una operación se haya completado.
  • Las pruebas deben incluir todo el recorrido realizado por el usuario.
  • Los errores deben analizarse como oportunidades de mejora y no para buscar culpables.
  • La documentación permite compartir el conocimiento con todo el equipo.
  • El control de versiones facilita la trazabilidad y revisión de los cambios.
  • En equipos remotos y ágiles, documentar decisiones y aprendizajes facilita la colaboración y evita depender de reuniones constantes.

8. Control de versiones

El proyecto fue documentado en un repositorio público de GitHub. Los cambios quedaron registrados mediante commits para mantener la trazabilidad del proceso.

9. Reflexión sobre el feedback radicalmente sincero

Durante la revisión recibí feedback sobre la claridad del contenido y la forma de explicar el problema. La devolución permitió identificar aspectos que podían resultar confusos y mejorar la estructura del blog.

Apliqué el feedback simplificando el lenguaje, explicando mejor el impacto del incidente, diferenciando las acciones correctivas de las preventivas e incorporando una cronología clara de lo sucedido.

Entendí que recibir una devolución sincera no significa tomarla como algo personal. Cuando el feedback es específico, respetuoso y orientado a mejorar, puede utilizarse para conseguir un resultado más claro y profesional.
